# Тестовое задание · Frontend (React + TypeScript)

## PokeMap Widget — встраиваемая карта-игра

Нужно сделать виджет: карта города с точками из OpenStreetMap, которые игрок
собирает, подходя к ним ближе заданного радиуса. Виджет поставляется одним
JS-файлом и встраивается в чужую страницу, которую вы не контролируете.

---

## Оценка

Оценивается: работа с императивным API карты из React, стратегия рендера большого
числа объектов, устойчивость слоя данных к реальному нестабильному API,
корректность интеграции в недружественное окружение, качество типов, чистота
жизненного цикла.

**Не оценивается: дизайн.** 

---

## Стек

Обязательно:

- **React 18+**
- **TypeScript** в строгом режиме: `strict`
- **MapLibre GL JS** напрямую. Обёртки вроде `react-map-gl` использовать
  нельзя — важно увидеть, как сшивается императивный жизненный цикл
  карты с реактивным жизненным циклом React.
- Сборка **Vite в library mode**, выход — один самодостаточный интегрируемый.

Свободно: стейт-менеджер, стилизация, тестовый фреймворк, всё остальное.

Данные берутся из публичных источников, прогресс хранится на клиенте.

---

## Данные

Точки — из **Wikipedia GeoSearch** (достопримечательности с описаниями и изображениями), тайлы — из **OpenFreeMap**. Ключи и регистрация не нужны.


Конкретные эндпоинты, параметры запроса, таблица редкости и список рекомендуемых городов — в [`docs/DATA.md`](./docs/DATA.md).

## Игровая механика

### Игрок

Маркер игрока в центре карты. Управление — на ваш выбор (перетаскивание маркера, клик по карте, кнопка «я здесь» от `navigator.geolocation`). Главное, чтобы игрока можно было переместить и это было очевидно.

### Сбор

- Точка доступна для сбора, если расстояние от игрока до неё **не больше 50
  метров**. Радиус настраивается через конфиг.
- Доступные точки визуально отличаются от недоступных и от уже собранных.
- Собранная точка не собирается повторно.

### Очки и комбо

- Базовые очки за точку определяются редкостью (таблица в `docs/DATA.md`).
- Каждый сбор увеличивает множитель комбо на `+0.2`, максимум `x3.0`.
- **Комбо сбрасывается в `x1.0` через 10 секунд после последнего сбора.**
- **При сборе точки редкости `epic` или `legendary` комбо замораживается на
  30 секунд.**
- Итоговые очки за точку: `базовые × текущий множитель`, округление вниз.

### Прогресс

- Сохраняется локально и переживает перезагрузку страницы.
- У хранилища есть версия схемы; данные несовместимой версии не должны ронять
  виджет.
- Есть сброс прогресса.

### Производительность

В плотном центре источник отдаёт сотни объектов за запрос, а при панорамировании с кэшем их накапливается кратно больше. Панорамирование и зум должны оставаться плавными. Какую стратегию рендера выбрать — на выбор исполнителя; в `DECISIONS.md` нужно назвать её предел: при каком количестве точек она перестанет работать и что делать дальше.

Маркеры: четыре редкости должны визуально различаться. У точек есть настоящие изображения с Викисклада, и они участвуют в интерфейсе — как минимум в карточке выбранной точки. Трафик и количество сетевых запросов при панорамировании должны оставаться разумными.

## Интеграция: host-page.html

Ключевая часть задания.

В корне репозитория лежит `host-page.html` — эмуляция zero-code конструктора,
в который поедет виджет. Файлы `host-page.html`, `host/cms-engine.js`,
`host/cms-theme.css`, `host/reference-widget.js` **менять нельзя**: при проверке
они будут заменены на исходные. Виджет подстраивается под окружение, а не
наоборот.

По умолчанию там подключена образцовая заглушка `host/reference-widget.js`. Она показывает интерфейс интеграции и **намеренно не решает** проблемы окружения — поводите по ней курсором, переключите масштаб полотна, сверните боковую панель. Замените её на свой бандл, когда будете готовы.

### Интерфейс интеграции

Виджет подключается **одним синхронным тегом `<script>`** и:

1. Сам находит контейнер `[data-widget="pokemap"]` и монтируется в него.
   Контейнер появляется в DOM **не сразу** после загрузки страницы, может быть
   удалён и создан заново (кнопки «пересобрать блок» и «стресс-тест ×5»).
2. Экспортирует программное API:

```ts
declare global {
  interface Window {
    PokeMapWidget: {
      readonly version: string;
      mount(target: string | HTMLElement, config?: PokeMapConfig): PokeMapHandle;
      unmount(handle: PokeMapHandle): void;
    };
  }
}

interface PokeMapConfig {
  city?: { name: string; center: [number, number] };
  collectRadiusMeters?: number;
  /** базовый URL источника точек, по умолчанию ru.wikipedia.org */
  apiBaseUrl?: string;
  onEvent?: (event: PokeMapEvent) => void;
}
```

3. Идемпотентен: повторный `mount` в тот же узел не создаёт второй экземпляр.
4. После `unmount` не оставляет следов: ни слушателей на `window`/`document`,
   ни таймеров, ни живых `requestAnimationFrame`, ни WebGL-контекстов.
5. Не ломает соседние блоки страницы и не перекрывает шапку конструктора.

### Режимы окружения

Кнопки в шапке включают три независимых режима. Проверять нужно каждый.

**Режим A — асинхронный слот.** Базовый. Блок с контейнером рендерится примерно
через 2 секунды после загрузки и пересоздаётся по кнопке.

**Режим B — плавающая раскладка.** Кнопка «панель» сворачивает боковую колонку,
ширина полотна меняется без перезагрузки и без события `resize` у окна.
Конструктор при этом бросает на `window` событие `cms:layout-changed`.

**Режим C — масштаб полотна.** Кнопки 80% и 125% применяют `transform: scale()`
к родительскому контейнеру. Режим ломает сразу
несколько независимых вещей, и починка каждой требует разного подхода.
Проверьте как минимум:

- попадает ли клик/перетаскивание туда, куда указывает курсор;
- где оказываются элементы с `position: fixed`, если они есть внутри виджета;
- какой размер получает холст карты и не замылен ли он.

## Дополнительный модуль (один на выбор)

Выберите **один** и обоснуйте выбор:

1. **Второй слой карты.** Теплокарта плотности точек или второй источник данных
   (например, кофейни из Geoapify) отдельным слоем с переключением видимости и
   корректным порядком отрисовки относительно маркеров.
2. **Синхронизация между вкладками.** Прогресс синхронизируется между
   открытыми вкладками в реальном времени, конфликты разрешаются осмысленно.
3. **Отчёт о производительности.** Замеры FPS и времени кадра при
   панорамировании до и после оптимизации, с методикой и цифрами.
